## 二、发布阻断问题（正式上线/试点前必须处理）

### B1. OCR 运行模式与文档/营销宣传不符 ⚠️ 最高优先

- **现象**：运行时实际为 **mock（演示）模式**，但法律文档与营销站均声称"on-device OCR 已上线/在设备端运行"。
  - 代码默认值：`src/lib/ocr/providers.ts:70` → `const mode = (process.env.EXPO_PUBLIC_OCR_MODE ?? "mock")` —— **默认 mock**。
  - 实际 `.env`：**未设置** `EXPO_PUBLIC_OCR_MODE`（已核实 `grep -c` = 0）→ 运行时回退到 mock，返回固定演示置信度 0.7/0.72，**不执行任何真实文字识别**。
  - `.env.example`：写的是 `EXPO_PUBLIC_OCR_MODE=device`（与代码默认矛盾）。
  - `docs/legal/AI_OCR_NOTICE.md §1`：声称 "The active provider is selected by `EXPO_PUBLIC_OCR_MODE` (**default device**)"、"On-device OCR is implemented... current production default"。
  - `site/index-zh.html:122 / :207`：营销页明示"设备端 OCR 提取候选字段"、"当前 OCR 在设备端运行"。
  - `PROGRESS.md`：声称"OCR 真实接入：on-device 已实施…已上线"。
- **后果**：若按当前 `.env` 出包，真实试点用户上传文档只会得到**假置信度**，且 mock 模式会显示"OCR 置信度为演示数据"横幅；同时法律/营销文档对用户做了"on-device 真实识别"的陈述 → **构成对用户的误导陈述**，合规与信任风险。
- **需你决策（二选一）**：
  - **方案 A（推荐，与文档对齐）**：让运行时真正跑 on-device。把 `providers.ts` 默认值改为 `"device"`，并在 EAS/原生构建环境与本地 `.env` 中显式设置 `EXPO_PUBLIC_OCR_MODE=device`；Expo Go 开发期手动切回 mock（注释说明）。优点：文档/营销/实现一致；缺点：Expo Go 不可用（需 prebuild，现状已如此）。
  - **方案 B（降文档）**：维持默认 mock，但修正 `AI_OCR_NOTICE.md`、`site/*`、`PROGRESS.md` 为"试点期使用演示置信度，on-device 已实现待启用"。优点：零代码风险；缺点：营销卖点削弱，且仍需在正式发布前切到 device。

### B2. cloud 模式下 Settings 误报"未启用云同步"

- **位置**：`src/App.tsx:1473`（`renderSettings` 内，无 cloud/local 分支）+ i18n key `settings.localSave`
- **现象**：`renderSettings` 对本地与 cloud 模式都渲染同一条提示：EN "Preview changes are saved on this device only. **No cloud sync is enabled.**" / 中文"预览改动仅保存在本设备。**当前未启用云端同步。**"
- **后果**：cloud 模式下数据实际写 Supabase 并实时多设备同步，但 UI 明确告诉用户"未启用云同步" → 与"换手机/删 app 数据还在"的核心卖点直接矛盾，用户可能误以为数据会丢。
- **修复方向**：按 `cloud` 分支渲染不同文案（cloud：说明云同步已启用 + 离线缓存；local：保留现有演示模式说明）。

### B3. Supabase 邮件确认（email confirmation）已关闭

- **位置**：`PROGRESS.md` 风险栏 + Supabase 项目配置
- **现象**：注册端点 email confirmation 关闭（开发测试用），任何人可用任意邮箱注册即登录。
- **后果**：无法验证账号归属，邀请/账号恢复/滥用防护均无保障；上线前必须开启。
- **修复方向**：Supabase Dashboard → Authentication → Email → 开启 "Confirm email"；配置 SMTP（或用 Supabase 默认邮件，注意免费额度）；`AuthScreen` 已有 "After signup, confirm via email if required" 提示，无需改代码。

### B4. 法律文档全部为 DRAFT，无生效日期，无 in-app 同意流程

- **位置**：`docs/legal/*.md`（5 份均标 DRAFT）、`site/privacy.md:72`（"公开发布前必须补充：生效日期"）、`docs/legal/COMPLIANCE_CHECKLIST.md §9`
- **现象**：隐私政策/ToS/临床免责/AI-OCR 通知/合规清单均为草稿；app 内**无任何**隐私政策/ToS 接受流程（首次启动/注册前未要求同意）。
- **后果**：隐私法（如 CalOPPA / CCPA）通常要求生效日期 + 可访问的政策 + 明示同意；当前缺失 = 合规门禁未过。
- **修复方向**：① 法律审阅并定稿 5 份文档 + 填生效日期；② app 内加首次启动同意流（注册前展示政策摘要 + "同意/不同意"）；③ Settings 内提供"查看隐私政策/ToS"入口。

### B5. 邀请链接以不可复制的 Alert 展示，核心邀请流程实际不可用

- **位置**：`src/App.tsx:483-484`
  ```ts
  const link = Linking.createURL("invite", { queryParams: { member: memberId } });
  showMessage("Invite link", link); // React Native Alert，正文不可选中/复制
  ```
- **现象**：协调人邀请成员后，邀请链接（或 member ID）通过 `Alert.alert` 展示。RN 的 Alert **不支持选中/复制**，协调人无法把链接发给被邀请人；被邀请人只能在 OnboardingScreen 手动输入 member ID（UUID）。
- **后果**："邀请家人加入照护圈"是核心 onboarding 流程，当前在 cloud 模式下基本无法完成。
- **需你决策（二选一）**：
  - **方案 A（推荐）**：改用 `Share.share` 或可复制的 Modal/Clipboard（`expo-clipboard`）展示链接/ID，并支持 deep link `taskkin-care://invite?member=<id>` 一键打开。
  - **方案 B**：暂用纯 member ID + 复制按钮（最小改动），deep link 作为后续增强。

## 三、重要问题（建议上线前修复，非绝对阻断）

### I1. cloud 写操作非原子（除任务流外），存在部分写入/孤儿文件风险

- **位置**：`src/lib/actions.ts`
- **现象**：
  - `confirmDocumentAndCreateTask`：依次执行 ① 更新文档状态 ② 插入 task ③ 插入 audit(document.confirmed) ④ 插入 audit(document.task_created) ⑤ 插入 role_notification —— **5 条语句不在同一事务**。任一步失败 → 状态不一致（如文档已 confirmed 但无 task / 无审计）。
  - `addDocument`：先 `storage.upload` 再 `documents.insert`；若 DB 插入失败，**文件已成孤儿**留在 Storage（无元数据、无清理）。
  - `addTimelineEvent` / `updateMemberRole` / `inviteMember` / `recordReportGenerated` 同理（多语句非事务）。
  - 对比：P0 任务流已用 `0006` 的 `create_task_with_activity` / `transition_task_with_activity` 原子 RPC 收敛；`PROGRESS.md` 待办也仅承认"文档确认待收敛"，实际范围更大。
- **后果**：网络抖动/部分失败时审计与业务状态漂移，违背"审计完整"硬要求。
- **修复方向**：将 `confirmDocumentAndCreateTask` 收敛为一个 security-invoker RPC（参照 `0006`）；其余多语句写操作至少补"失败回滚/重试/孤儿清理"。`addDocument` 在 DB 插入失败时删除已上传的 storage 对象。

### I2. OCR 候选字段/原始文本/坐标未持久化，但法律文档声称"保留"

- **位置**：`backend/supabase/migrations/0001`/`0004`（`documents` 表无 `raw_text`/`fields`/`bounding` 列）、`src/lib/actions.ts`（`addDocument` 未使用 `ocr.rawText`/`fields`）、`docs/legal/AI_OCR_NOTICE.md §2`
- **现象**：`DeviceOcrProvider` 计算出 `fields`、`rawText`、`suggestedAction`，但 `addDocument` 只写 `confidence` 与 `suggestedAction`；`rawText` 与 `fields`（含 bounding box）**计算后即丢弃**。而 `AI_OCR_NOTICE.md §2` 明示 "The original file and source coordinates (bounding boxes) are retained for traceability."
- **后果**：法律文档与实现不符；OCR 可追溯性承诺落空。
- **修复方向（二选一）**：① 给 `documents` 表加 `raw_text text` / `extracted_fields jsonb` 列并持久化；② 修正 `AI_OCR_NOTICE.md` 措辞为"仅保留原始文件与置信度，候选字段为瞬时计算结果"。

### I3. `accept_invite` 不绑定受邀者身份（凭 UUID 即可加入）

- **位置**：`backend/supabase/migrations/0002_rls_and_rpc.sql`（`accept_invite`）
- **现象**：RPC 仅校验 `invite_status='pending' and user_id is null and 未过期`，**不校验调用者是否为协调人指定的那个被邀请人**（无邮箱/token 绑定）。任何持有 pending member UUID 的已注册用户都能接受该邀请。
- **缓解**：member id 为 `gen_random_uuid()`，不可猜测；邀请 48h 过期。但链接一旦泄露即可被冒用。
- **修复方向**：邀请时记录目标邮箱（`members.invite_email`），`accept_invite` 校验 `auth.jwt() ->> 'email' = invite_email`；或改用 Supabase OTP 邀请链接。

### I4. 依赖漏洞（11 个，均在 Expo SDK 传递依赖）

- **位置**：`npm audit`
- **高危**：`brace-expansion`（DoS，via `expo → @expo/fingerprint → minimatch → brace-expansion`）
- **中危**：`uuid`（via `expo → @expo/config-plugins → xcode → uuid`）等
- **性质**：全部为**构建期/工具链**传递依赖，非 app 运行时依赖；移动端无服务端正则攻击面，实际可利用性低。
- **现状**：`.github/workflows/ci.yml` 中 security job `continue-on-error: true`（信息性，不阻断）。
- **修复方向**：升级 Expo SDK 至清除该传递漏洞的版本（breaking，需回归）；或在风险接受记录中说明"构建期、不可利用"并保留 `continue-on-error`。**不建议** `npm audit fix --force`（会强升 expo 到 46.x）。

### I5. iOS / Android 应用标识命名空间不一致（请确认是否有意）

- **位置**：`app.json`
  - iOS `bundleIdentifier`: `cd.cc.relaycare`
  - Android `package`: `care.taskkincare.app`
  - slug: `taskkin-care`，display name: `TaskKin Care`，目录: `relaycare-mvp`
- **背景**：`docs/QA_Log.md` 记录 iOS `cd.cc.relaycare` 为"Apple 已注册标识"。但 Android 用了完全不同的反向域名。
- **后果**：双端应用商店/品牌命名不统一；若后续做 universal link / app link，域名映射会混乱。
- **需你确认**：是否双端各自独立注册所致（若是，建议在 README 记录原因）；若非有意，建议统一为同一命名空间。

## 四、工程卫生与打磨（P2/P3，可试点后处理）

### P2-1. 角色推送过滤隐式依赖 Realtime RLS

- `src/lib/db.ts:subscribeRoleNotifications` 订阅家庭全部 `role_notifications` INSERT，**不在客户端按 audience 过滤**就 `scheduleNotificationAsync`。当前靠 Supabase Realtime 对 `notifications: select audience` RLS 策略的强制只投递受众匹配的 payload（正确，但**隐式且脆弱**）。建议在 `onNew` 回调里加一道 `audience === 'all' || audience === actor.role` 防御性过滤。

### P2-2. 列表顺序非确定

- `src/lib/db.ts:fetchHouseholdState` 只对 `audit_events` 做 `order by`，tasks/members/documents/events 均未排序 → DB 返回顺序不定，Tasks 标签页任务顺序会随每次实时刷新跳动。建议各查询补 `order by created_at` / `due_at`。

### P2-3. 实时同步每次全量重拉

- `subscribeHouseholdState` 监听 7 张表任一变更即触发 `fetchHouseholdState`（9 路并行查询）。连续操作会产生多次全量重拉（闪烁/竞态）。小家庭可接受；可改为 debounce 或按表增量更新。

### P2-4. `app.json` 缺生产配置

- 无 `splash`、`assetBundlePatterns`、iOS `infoPlist` 用途描述（`NSPhotoLibraryUsageDescription` / 文档访问等）。`@dariyd/react-native-text-recognition` 与 `expo-document-picker` 在 App Store 审核时可能要求用途说明。原生 build 已通过（用默认），但上架前需补 infoPlist。

### P3-1. `0002` 两个 RPC 未显式收回 public 执行权

- `create_household` / `accept_invite`（security definer）未像 `0006` 那样 `revoke ... from public; grant execute ... to authenticated;`，仅靠函数内 `auth.uid() is null` raise 兜底。功能安全，但权限卫生不一致。建议补 revoke/grant。

### P3-2. `all_in_one.sql` 注释过时

- `backend/supabase/all_in_one.sql:3` 注释"Apply the numbered files in migrations/ through 0005"，但 `backend/README.md` 已更新到 0006。该文件已标 DEPRECATED，建议把注释改为"through 0006"或直接删除该文件避免误用。
